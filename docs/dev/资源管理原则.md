# CCMake 资源管理原则

本文冻结 CCMake 的资源管理策略。旧代码中的 `CMKLimits`、`CCMakeCCMLimits` 等字段保留为**可选实现预算**，但默认不设置语言能力上限；0 表示由实际内存、地址空间和表示边界约束。

## 1. 三层策略

### 1.1 第一层：安全边界

以下约束不可关闭，任何输入都必须正确处理：

- 所有分配尺寸检查整数溢出；
- 数组容量扩张检查 `count * sizeof(T)` 与 `old + new` 加法溢出；
- 文件读取检查宿主可表示长度，拒绝不可表示的文件；
- 资源创建与释放严格对称；
- 所有失败路径可回滚；
- 进程、文件、目录、VFS 句柄可回收；
- 不允许用“固定上限”代替上述检查。

实现落点：

| 位置 | 要求 |
|---|---|
| `ccalloc` 调用前 | 检查 `len + 1`、`count * size` 不溢出 |
| `CCDyn` 扩容前 | 检查元素宽度与元素数量乘积、`CCUINT32` 表示边界 |
| `.ccm` 文件读取 | `size == UINT64_MAX` 或 `size > SIZE_MAX - 1` 拒绝 |
| `.cmk` 文件读取 | 同上，并拒绝 `ftell` 不可表示的结果 |
| Parser/AST/Program 析构 | 按所有权逆序释放，失败路径不发布半成品 |
| 文件/目录/VFS | `create/open` 成功后才登记所有权；失败路径关闭 |

### 1.2 第二层：动态资源，不设默认硬上限

以下资源默认动态增长，只有在实际分配失败时返回“内存分配失败”：

| 资源 | 目标 |
|---|---|
| Token 数量 | 动态 |
| AST 节点数量 | 动态 |
| 变量数量 | 动态 |
| 列表元素数量 | 动态 |
| 字符串长度 | 动态 |
| Target 数量 | 动态 |
| Target 依赖数量 | 动态 |
| Action 数量 | 动态 |
| 导入模块数量 | 动态 |
| 文件查找结果数量 | 动态 |

- `CMKLimits` 的计数类字段默认 0；`0` 表示不限；
- `CCMakeCCMLimits` 的计数类字段默认 0；`0` 表示不限；
- 不再因为 `max_list_elements`、`max_array_elements`、`max_find_results` 等固定值拒绝追加；
- 扩容失败必须返回明确的内存错误，并保持已有资源可释放；
- 动态数组的 `CCUINT32` 表示上限仍是硬边界，但它是表示边界，不是用户配置上限。

### 1.3 第三层：可配置执行策略

这些限制是执行策略，不是语言能力上限；默认 0（不限），由用户或宿主按需设置：

| 策略 | 建议字段 | 默认 |
|---|---|---|
| 最大递归深度 | `max_recursion_depth` | 0 |
| 最大 Configure 执行时间 | `max_configure_time_ms` | 0 |
| 最大执行步数 | `max_steps` | 0 |
| 最大文件查找深度 | `max_find_depth` | 0 | 已接入 `find_files` |
| 最大并发进程数 | `max_processes` | Scheduler / `-j` | 已接入 READY 批次 |
| 最大输出捕获大小 | `max_output_capture` | Executor/Process | 已接入 |

- 执行时间和步数不能默认限制正常构建脚本；
- `CMKExecutionPolicy` 默认全 0；Runtime 已接入 `max_steps`、`max_recursion_depth`（显式脚本帧栈）与 `max_configure_time_ms`（`clock()` CPU 时间），`max_find_depth` 已接入 `find_files`，`max_output_capture` 已接入 Executor/Process；
- `CMKProgram` 提供 `cmk_program_set_policy`，在 Configure 前把策略下发到各模块 Runtime；
- `CMKProgram` 创建时读取环境变量：`CCMAKE_CMK_MAX_STEPS`、`CCMAKE_CMK_MAX_RECURSION_DEPTH`、`CCMAKE_CMK_MAX_CONFIGURE_TIME_MS`、`CCMAKE_CMK_MAX_FIND_DEPTH`、`CCMAKE_CMK_MAX_PROCESSES`、`CCMAKE_CMK_MAX_OUTPUT_CAPTURE`；未设置或 0 表示不限；
- 若 `max_processes` 仍为 0，Program 继承命令行 `-j/--jobs` 的并发值；
- 策略失败必须产生可定位诊断，并释放当前执行状态；
- `-j` 属于并发策略，不属于语言语义。

## 2. 递归与显式堆栈

原则：

1. CMK 语言调用深度不设人为固定上限；
2. 随输入深度增长的递归路径不得直接消耗宿主 C 栈；
3. 堆栈扩容失败时返回内存分配错误，释放当前执行状态，不破坏 Runtime/Program 所有权；
4. 已经使用显式堆栈的模块不得回退为递归。

迁移矩阵：

| 模块 | 递归路径 | 方案 | 状态 |
|---|---|---|---|
| AST | 销毁、校验、visitor | 显式节点栈/连续数组 | 已完成（validate/visit 使用显式栈；destroy 遍历连续数组） |
| Program | 模块导入 DFS | 显式加载帧栈 | 已完成（`CMKProgramLoadFrame`） |
| Parser | 嵌套表达式、类型、语句、声明 | 显式解析帧栈 | 已完成：类型、一元、表达式、语句/块/if/while/for、target 顶层 if |
| Semantic | 嵌套作用域、语句/表达式检查 | 显式遍历栈 | 已完成：块/if/while/for、表达式、target 顶层 if 均使用显式栈 |
| Runtime | 函数递归、表达式求值、语句执行 | 显式脚本帧栈 + 表达式程序栈 | 完成：语句、if、while、for-in、break/continue、赋值、条件、return 表达式、跨模块调用均由显式脚本栈驱动；
| Build Graph | 依赖解析、拓扑排序、root 闭包 | 显式队列/数组 | M5/M6 已采用 |

在迁移完成前，Parser/Semantic/Runtime 仍使用 C 递归；这是当前实现的已知偏离，不能通过设置一个固定深度上限来宣称满足原则。

## 3. 默认值调整

- `cmk_limits_init`：`max_syntax_depth = 0`、`max_expression_depth = 0`；
- `ccm_context_init`：所有计数/深度字段为 0；
- 所有 `max_* != 0` 的判断都必须在 0 时跳过；
- 测试中需要验证预算时显式设置字段，不再依赖默认硬上限；
- 默认路径的测试验证“0 = 不限制”，并用中等规模输入做回归。

## 4. 失败与回滚

- 分配失败不发布半成品 AST/Plan；
- Parser 失败销毁临时 AST；
- Semantic/Runtime 失败由 Program 统一销毁模块；
- `@include`/`@import` 失败释放已加载的 CCM 上下文、AST、Semantic、Runtime；
- Builtin 失败写诊断并清理输出值；
- 文件打开/挂载成功后必须登记，失败路径关闭；
- 错误诊断不设固定长度，动态分配。

## 5. 测试

- 溢出边界：文件长度、字符串长度、动态数组尺寸；
- 默认 0 限制：大列表、大 token 流、深但合理的嵌套；
- 显式预算：设置小值验证诊断，然后恢复 0；
- 失败回滚：解析/语义/运行时失败后重复使用新上下文；
- 显式堆栈：模块导入、AST visitor 的深输入；
- 所有权：Debug 全量测试无 `ccalloc` 泄漏。

## 6. 当前状态

已落地：

- 默认计数/深度预算改为 0；
- CCM 预算检查全部支持 0 跳过；
- CCM 诊断去除固定 1024 字节缓冲；
- `.ccm` 文件读取增加可表示长度检查；
- `.cmk find` / `.ccm` 路径拼接增加 `size_t` 加法溢出检查；
- AST validate/visit 已是显式栈；
- `.ccm` 值解析的嵌套对象/数组已改为 `CCMValueFrame` 显式栈；
- CCM 动态数组追加统一走 `ccm_dyn_push`，检查尺寸加法与表示边界；
- `ccvar`、`cmd` 的动态数组追加也统一走带边界检查的本地包装，`src` 内直接 `cc_dyn_core_push` 只保留在安全包装内部；
- Program 模块导入 DFS 已改为显式加载帧栈；
- Parser 类型解析、一元运算链、表达式（括号/列表/调用/索引/成员）、语句/块/if/while/for、target 顶层 if 已改为显式栈（5000 层类型、一元、块、if、括号、列表、调用、顶层 if 压力测试通过）；
- Semantic 的块/if/while/for 检查已改为 `CMKSemFrame` 显式栈（5000 层块/if 语义测试通过）；
- Semantic 表达式检查已改为 `CMKSemExprFrame` 显式栈（5000 层二元/一元/调用语义测试通过）；
- Semantic target 顶层 if 预收集与分析已改为显式栈（5000 层测试通过）；
- Runtime 的 target 顶层 if 已改为显式栈（5000 层 Configure 测试通过）；
- Runtime 表达式求值与调用实参已改为 `CMKRtExprFrame` 显式栈（5000 层二元/一元/列表/索引/嵌套调用测试通过）；
- Runtime 直接尾递归 `return f(...)` 改为迭代调用循环，不消耗 C 栈（5000 层尾递归测试通过，`max_recursion_depth` 仍按逻辑调用计数）；
- Runtime 线性非尾递归（如 `return 1 + f(n-1)`）改为延续栈迭代，调用返回后逆序应用 continuation；
- Runtime return 表达式中的分支递归改为表达式字节码 + 程序栈，`f(n-1)+f(n-2)` 通过挂起/恢复调用栈执行；
- 非 return 表达式（赋值、条件、循环、target 字段）中的函数调用改由 Runtime 通用语句上下文 VM 执行；调用以脚本帧形式压入显式脚本栈，不再逐层进入 C 递归；
- Runtime 的块/if/while/for 执行由语句 VM 的显式帧栈驱动（5000 层块/if 与 for-in/break/continue 测试通过）；
- `find_files` 目录遍历已改为显式目录栈，并接入 `max_find_depth`；
- Runtime 已接入 `CMKExecutionPolicy.max_steps`、`max_recursion_depth` 与 `max_configure_time_ms`；
- Value/Builtin/Semantic/Runtime/Program 的默认动态资源路径已有测试。

已补齐：

- Cache 通过 `CMKCacheOps` 接入 Scheduler 的 SKIPPED；`-B` 强制绕过；
- 进程取消使用 Windows Job Object / POSIX 进程组，覆盖子进程树；
- 并发 Executor 输出统一由 Scheduler 按稳定顺序写 stdout。

后续增强：

- fail-fast 立即取消正在运行的批次（当前批次粒度）；
- 进程树终止宽限期可配置。
