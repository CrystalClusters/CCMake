# CCMake 代码治理规范

本规范约束功能开发与重构。

## 1. 目标

恢复并保持：

- 模块所有权清晰；
- 接口权限明确；
- 实现简洁；
- 文档与代码一致；
- 每次修改可构建、可测试、可回滚。

不以文件数量、代码行数或抽象层数量作为治理成果。

## 2. 六个持续方向

| 方向 | 要求 |
|---|---|
| G1 死代码 | 禁止保留 `#if 0`、`if (0)`、`legacy` 实现 |
| G2 函数复杂度 | 超过 100 行说明原因，超过 200 行原则上拒绝 |
| G3 模块边界 | 私有结构体不进入通用头文件，跨模块只走明确接口 |
| G4 文件结构 | 文件职责与模块职责一致，禁止为拆而拆 |
| G5 规范一致性 | 所有权、错误处理、命名、格式统一 |
| G6 文档与硬编码 | 文档对应当前实现，默认策略集中定义 |

## 3. 权限规则

- 模块只能操作自己拥有的数据；
- 冻结后的 Plan 只能通过受控状态接口修改；
- 构造期写入接口与只读查询接口分开；
- 跨模块访问内部字段必须通过内部头文件或访问器；
- 不允许为了隐藏结构体制造新的循环依赖。

## 4. 复杂度规则

- 控制流嵌套达到 5 层必须审查；
- 巨型函数按职责拆分，不按行数机械切割；
- 不增加只转发参数的包装函数；
- 状态机按节点类型/阶段拆分时，共享帧必须显式定义所有权。

## 5. 资源与错误

- 拥有资源的接口必须明确释放责任；
- 失败路径必须回滚，不发布半成品；
- 动态增长失败必须显式报错；
- 普通资源不设置固定硬上限；
- 公开写入接口检查整数溢出、容量和表示范围。

## 6. 每批治理流程

1. 扫描并记录问题：文件、函数、行号、类型、严重程度；
2. 确认引用关系；
3. 只做一类修改；
4. 构建 Debug/Release；
5. 跑全量测试；
6. 记录本批修改范围与验证结果；
7. 单独提交，提交信息说明治理范围。

## 7. 质量门禁

提交前至少执行：

```bat
build.bat
build.bat release
test.bat
git diff --check
```

静态分析使用 `gcc -fanalyzer`；构建与测试不依赖 Python。

门禁由 Release `-Werror`、全量测试与 `git diff --check` 组成。

死代码、函数长度、公共头依赖由代码审查检查；全仓 `-fanalyzer` 为可选静态分析，不引入 Python 或外部检查工具。

Sanitizer / 失败路径测试不在当前 MinGW 环境内运行。

## 8. 文档规则

- README 只描述当前可执行流程与测试入口；
- 设计文档只描述当前行为、接口和边界；
- 删除过时阶段性描述；
- 硬编码默认值必须说明来源和配置入口。
